# 版本发布流程（GitHub Actions + 自动更新）

本仓库的发版链路有两条，按需选择：

- **路径 A（CI 全自动，推荐用于正式发版）**：本地改版本号 → 提交 → 打 `v*` tag 并 push，
  触发 `build-release.yml`（Windows 构建 → 签名 → 发布 GitHub Release + `latest.json`）→
  应用内"检查更新"自动升级。
- **路径 B（本地签名构建，适合不想走 / 未配 GitHub Secrets 时）**：本地 `pnpm tauri build`
  直接产出签名好的 NSIS 安装包；**不会**自动生成/发布 `latest.json`，需自行上传。
  v0.3.0 即用此路径交付。

> 路径 A 需要先配置 GitHub Secrets（见 §一），否则 CI 签名步骤会失败（刻意设计——
> 不带签名的安装包不能走自动更新）。

---

## 一、一次性前置（首次发版前）

| 项 | 状态 | 说明 |
|---|---|---|
| GitHub 仓库 | ✅ | `backunderstar/ToolBox`（公开） |
| updater endpoints | ✅ | `tauri.conf.json` 已指向 `https://github.com/backunderstar/ToolBox/releases/latest/download/latest.json` |
| 签名公钥 | ✅ | `tauri.conf.json` `plugins.updater.pubkey` 已写入 |
| 本地签名私钥 | ✅ | `C:\Users\admin\.tauri\toolbox-updater.key`（**在仓库外，切勿提交**） |
| **GitHub Secrets** | ⬜ | 见下，需在仓库设置里手动配置一次（路径 A 必需） |

### 配置 GitHub Secrets

打开 <https://github.com/backunderstar/ToolBox/settings/secrets/actions> → **New repository secret** ×2：

| Name | Value |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | 私钥文件**内容**（含 `-----BEGIN … END-----` 全部行）。取内容：<br>`Get-Content -Raw C:\Users\admin\.tauri\toolbox-updater.key` |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | `tb-updater-key` |

> Secrets 只在 GitHub Actions 运行时注入，一旦保存不可再查看；改密码需删掉重建。
> 未配置 secrets 时，CI 里 `pnpm tauri build` 的签名步骤会失败（这是刻意的——不带签名的安装包不能走自动更新）。
> 配置完成后，路径 A 的 tag 推送即从"构建失败"变为"自动发布"。

## 二、升版本号（版本单源）

**`package.json` 的 `version` 是唯一来源**，其余各处由脚本同步：

```powershell
# 1. 改 package.json 的 version（语义化版本，如 0.2.0 → 0.3.0）
# 2. 同步到 tauri.conf.json / src/core/version.ts / 4 个 crate 的 Cargo.toml
pnpm version:sync

# 3. 校验同步结果（CI 用 --check，版本漂移即失败）
node scripts/sync-version.mjs --check
# 或 git diff --stat  查看改动
```

同步范围（`scripts/sync-version.mjs` 写死，改 crate 需同步改它）：

- `src-tauri/tauri.conf.json`（`version`）
- `src/core/version.ts`（`APP_VERSION` / 顶栏 tag `APP_TAG = "v<版本>"`）
- 4 个 crate 的 `Cargo.toml`（`[package] version`）：
  `src-tauri`、`tb-sdk`、`core-plugins/example`、`core-plugins/probe-rat-layer`

> ⚠️ 不要手动改各 Cargo.toml / tauri.conf.json 的版本——`pnpm version:sync` 会覆盖。

## 三、本地预检（发版前建议跑一遍）

```powershell
pnpm lint          # oxlint
pnpm build         # tsc typecheck + 前端构建（CI 用 pnpm typecheck 只做类型检查）
pnpm test          # vitest 纯函数单测
cargo clippy --workspace --all-targets --no-deps -- -D warnings      # CI 同款（debug 档）
cargo clippy --workspace --all-targets --no-deps --release -- -D warnings  # release 档（打包前务必跑）
cargo test --workspace
```

> CI 的 clippy 跑在 debug 档（`cfg(dev)` 生效），**打包版跑在 release 档**（`cfg(dev)` 不生效）。
> 只有 release 档的 `-D warnings` 才能真正拦住"仅 release 触发的 dead_code/unused"——本次 v0.3.0
> 就清理了一处 `save_removed_bundled`（release 才报、CI debug 不报）的 dead_code 警告。
> 所以**打包前应跑 release 档 clippy**，别只在本地 debug 档过一遍。

## 四、路径 A：提交并打 tag（CI 发版）

```powershell
git add -A
git commit -m "release: v<版本>"        # 例如 release: v0.3.0
git push origin main

git tag v<版本>                          # tag 名 = v + package.json version
git push origin v<版本>
```

push tag 即触发 `build-release.yml`（`on: push: tags: ["v*"]`），无需其他操作。

---

## 五、路径 A：自动流程（build-release.yml 做什么）

1. Windows runner 上：`pnpm install` → `pnpm typecheck` → `pnpm fetch:python`（下载捆绑 Python 运行时）→ `cargo test --workspace`
2. `pnpm tauri build`（`beforeBuildCommand` 先构建核心插件 release DLL + 前端）
3. 用 Secrets 里的私钥为安装包生成 updater 签名（`.sig`）
4. 生成 `latest.json`（含 version / signature / 安装包下载 URL）
5. 发布 GitHub Release（`v*` tag），附带 `*-setup.exe` + `.sig` + `latest.json`

产物在 workspace 根 `target/release/bundle/nsis/`。

## 六、路径 B：本地签名构建（不使用 CI）

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = (Get-Content -Raw "C:\Users\admin\.tauri\toolbox-updater.key")
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = "tb-updater-key"
pnpm tauri build
```

产物（确认存在 `.sig` 才算签名链路 OK）：

```
target\release\bundle\nsis\ToolBox_<版本>_x64-setup.exe
target\release\bundle\nsis\ToolBox_<版本>_x64-setup.exe.sig
```

> ⚠️ 路径 B **不会**生成 `latest.json`（那一步在 build-release.yml 的 bash 步骤里）。
> 若要让应用内"检查更新"生效，需把 `exe` + `.sig` 上传到 GitHub Releases 的某个 tag，
> 并手工准备 `latest.json`（格式见 build-release.yml 第 99-111 行）一并上传。
> 只做本地分发、不做更新链路的话，单靠 `exe` 即可（v0.3.0 即此情形）。

## 七、发版后验证

- **路径 A**：
  - **Actions**：<https://github.com/backunderstar/ToolBox/actions> 查看 run 状态（约 10-15 分钟）
  - **Releases**：<https://github.com/backunderstar/ToolBox/releases> 确认 tag 与 3 个资产
  - **latest.json 可访问**：<https://github.com/backunderstar/ToolBox/releases/latest/download/latest.json>
  - **应用内升级**：设置页 →「检查更新」（或下次启动检查）→ 提示下载并安装新版本
- **路径 B**：把安装包分发出去即可；更新链路需按 §六 补 `latest.json`。

## 八、常见问题

- **CI 的 `pnpm tauri build` 步骤失败**：几乎都是 Secrets 未配置/配置错误（签名失败）。
  检查 Settings → Secrets 是否两个都已添加。
- **CI 偶发失败**（如 `cargo test` 里 python 桥接测试超时、`pnpm audit` 网络抖动）：
  到 Actions 页点该 run 的 **Re-run**，或空提交重推 `git commit --allow-empty -m "ci: rerun" && git push origin main`。
- **tag 打错**（未推送前可安全删）：
  ```powershell
  git tag -d v0.1.0
  git push origin :v0.1.0   # 已推送时删除远端 tag
  ```
- **发版后想改版本号**：走 §二 流程升版本，重新打新 tag；`latest.json` 会被新 Release 覆盖
  （endpoint 用的是 `releases/latest`，始终指向最新版）。
- **私钥安全**：私钥只存在于本机与 GitHub Secrets；一旦泄露需重新生成密钥对并更新
  `tauri.conf.json` 的 pubkey（`tauri signer generate` 生成，见 Tauri 文档）。
- **想要"不发布也能更新"**：走路径 B（本地签名），但需要自建 `latest.json` 托管
  （可先放到本地/内网，把 `tauri.conf.json` 的 endpoint 指向它）。
