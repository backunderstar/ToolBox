# ToolBox 技术栈与概念详解（学习指南）

> 配套阅读：`docs/操作手册.md`（项目结构/逻辑/打包/使用，偏实操）
> 本文档：把项目里用到的**技术栈和核心概念**逐个讲透，供系统学习。
> 阅读顺序：第 1 节（架构心智模型）→ 第 2/3 节（前后端技术栈）→ 第 4 节（核心概念）→ 第 5/6 节（调试与学习路线）。

## 1. 架构心智模型（先建立这张图）

```
┌────────────────────────────────────────────────┐
│  ToolBox 桌面应用（Tauri 2）                     │
│                                                │
│  ┌── Rust 核心（主进程，src-tauri/）─────────┐  │
│  │  · 命令注册中心（lib.rs）                 │  │
│  │  · 文件系统 / 搜索 / AI / 博客 / 插件管理   │  │
│  │  · 所有"碰磁盘、碰网络、起进程"的事        │  │
│  └──────────────────────────────────────────┘  │
│            ▲ invoke（IPC 桥）                   │
│            │  JSON 参数/返回值                  │
│  ┌── WebView 前端（渲染进程，src/）─────────┐  │
│  │  · React 19 + TypeScript                  │  │
│  │  · 状态层（vault/plugins/checklists…）     │  │
│  │  · 视图层（笔记/插件/工具/清单/博客…）      │  │
│  └──────────────────────────────────────────┘  │
└────────────────────────────────────────────────┘
                │
                ▼ 读写
        ┌────────────────┐
        │  vault 工作区   │  ← 用户的"数据主权"文件夹
        └────────────────┘
```

**三个核心认知**：

1. **前端 ≠ 后端**：React 只负责界面和状态；所有文件读写、网络请求、子进程都在 Rust 里做，前端通过 `invoke("命令名", 参数)` 调用。好处：安全（前端拿不到任意路径权限）、性能（重活不卡 UI）。
2. **"数据永远是用户的"**：整个应用不建私有数据库，所有内容都是 `vault/` 文件夹里的普通文件（Markdown / JSON）。关掉应用、删掉应用，数据还在，随时可以用 git/网盘/手动复制备份。
3. **命令即接口**：Rust 侧每个 `#[tauri::command]` 函数就是一个可被前端调用的 API；前后端之间的"接口文档"就是这些命令的签名。

## 2. 前端技术栈（src/）

### 2.1 React 19
- **组件**：`function XxxView(props)`；视图组件（NotesView/PluginsView…）→ 组合组件（Editor/FileTree…）。
- **Hooks 三件套**：
  - `useState`：本地状态（如编辑器是否忙碌、搜索词）
  - `useEffect`：副作用（挂载时加载数据、监听键盘事件）
  - `useMemo / useCallback`：缓存计算和函数引用，避免无效重渲染
- **Context + Provider 模式**（本项目状态管理的核心）：
  ```tsx
  // src/core/vault.tsx —— 整个"工作区"状态的唯一来源
  const VaultContext = createContext<VaultContextValue | null>(null);
  export function VaultProvider({ children }) { ... }
  export function useVault() { return useContext(VaultContext); }
  ```
  所有笔记相关状态（路径、文件树、当前文件、内容、脏标记）集中在一个 Provider 里，任何组件 `useVault()` 就能读写。项目里有 5 个这样的 Provider：`vault / plugins / checklists / records / navigation`。
- **为什么要用 Provider 而不是全局变量**：状态变化时只有订阅的组件重渲染；切文件、自动保存等联动逻辑集中管理，避免"到处 setState"。

### 2.2 TypeScript
- 给 JavaScript 加类型：`interface VaultContextValue`、`type ViewId = "notes" | "plugins" | ...`。
- 项目里的典型用法：
  - 前后端数据类型对齐（`FileEntry`、`SearchHit` 在 `api.ts` 里声明，与 Rust 的 `serde` 结构体字段一一对应）
  - 字符串字面量联合类型做"枚举"（如 `PluginInfo.status: "ready" | "stopped" | "error"`）
  - `pnpm build` 会先跑 `tsc` 做类型检查，等于给前端上了一道"编译期防线"。

### 2.3 Vite（构建工具）
- 开发时：`pnpm dev` 起本地服务器（端口 1420），改代码即时热更新（HMR）。
- 构建时：`pnpm build` → `tsc`（类型检查）→ `vite build`（打包成 `dist/`）。
- 本项目对构建做了**分包**（vite.config.ts 的 `manualChunks`）：vditor 单独一个 chunk、react 单独一个 chunk。原因：vditor 体积大（~300KB）且更新频率低，独立成包可以缓存、并行加载。

### 2.4 Vditor（Markdown 编辑器）
- 三种编辑模式：
  - **分屏预览**（Split）：左边写 Markdown 源码，右边实时预览
  - **所见即所得**（WYSIWYG）：像 Word 一样直接编辑渲染结果
  - **即时渲染**（IR，本项目用的）：**边写边渲染**——光标所在行显示源码语法，其他行显示渲染效果（Typora 风格）。源码可视性 vs 渲染直观性的折中。
- IR 模式依赖 **Lute**（字节跳动开源的 Markdown 引擎），本地化在 `public/vditor/dist/`，所以**离线可用**。
- 本项目对 Vditor 的定制（Editor.tsx）：
  - 关闭不用的工具栏项（上传/表情/大纲/字数统计）
  - 自定义 AI 摘要按钮：选中文本 → 调 AI → 以引用块替换选区
  - 主题跟随（深色模式传 `theme: "dark"`）
  - **关键坑**：Vditor 3.x 会把 `vditor` 类加到宿主元素本身，且部分样式是运行时内联注入的（比如工具栏 35px 内边距）——所以要覆盖它的样式时用 `!important`（见 app.css 里的 `.editor-host .vditor-toolbar`）。

## 3. 后端技术栈（src-tauri/）

### 3.1 Rust（语言本身）
项目用到的最核心语法：
- **所有权 / 借用**：`&self`（只读借用）、`&mut self`（可变借用）、`move` 闭包。典型例子：`PluginManager` 被 `Mutex` 包住，命令里 `m.lock()` 拿到可变引用才能改。
- **Result / Option**：Rust 没有异常，函数返回 `Result<T, E>` 或 `Option<T>`；命令签名 `-> Result<Vec<PluginInfo>, String>` 里的 `Err` 会直接变成前端 `invoke` 抛出的错误。
- **`?` 运算符**：`std::fs::read_to_string(&p).map_err(|e| ...)?`——出错就提前返回。
- **async**：`async fn` 命令不会阻塞 Tauri 主线程，重活（读大文件、网络请求）不卡 UI。
- **trait**：`Serialize`（序列化）、`Default`、`Drop`（如 `ProcessPlugin` 的 Drop 实现进程清理）。

### 3.2 Tauri 2（应用框架）
- **命令系统（IPC）**：Rust `#[tauri::command]` + `.invoke_handler(tauri::generate_handler![...])` 注册；前端 `invoke("fs_list", { vault })` 调用。参数和返回值自动走 JSON 序列化。
- **State 管理**：`app.manage(Mutex::new(PluginManager::default()))` 注册全局状态，命令里 `State<'_, Mutex<PluginManager>>` 取用。用 `Mutex` 是因为命令可能是并发的，需要互斥。
- **能力系统（capabilities）**：`src-tauri/capabilities/default.json` 声明窗口能调哪些插件能力（如 `core:default`、`dialog:default`、`opener:default`）。这是 Tauri 2 的安全边界——前端默认不能随便调系统能力。
- **事件（Event）**：Rust 侧 `app.emit("事件名", data)` → 前端 `listen("事件名", cb)`。用于跨窗口/异步通知（后续浮窗清单的双窗同步就用它）。
- **多窗口**：`WebviewWindowBuilder` 或 tauri.conf.json 的 `windows[]`（浮窗方案的基础）。
- **开发调试**：`additionalBrowserArgs: "--remote-debugging-port=9226"` 可让 WebView2 暴露 CDP 端口，用脚本驱动真实窗口做 E2E（见第 5 节）。

### 3.3 序列化与文件
- **serde / serde_json**：Rust 结构体 ⇄ JSON。
  ```rust
  #[derive(Serialize)]
  #[serde(rename_all = "camelCase")]  // Rust 的 snake_case → 前端 camelCase
  pub struct FileEntry { pub name: String, pub path: String, pub is_dir: bool }
  ```
  `rename_all = "camelCase"` 是 Rust/JS 命名风格差异的常见解法。
- **路径安全（core/path.rs）**：所有"用户传入的相对路径"都要过 `resolve_safe`：
  - 拒绝空、`.`、`..`、绝对路径、盘符前缀
  - 拼出绝对路径后校验父目录 == vault 根（防 `../` 越界）
  - 这是"纯文件应用"最重要的安全防线。

### 3.4 插件系统（M2 里程碑的核心）
- 两种运行时：
  - **webview 插件**（JS）：前端 `new Function("api", code)` 求值入口文件，插件通过 `api.app.registerCommand` 注册命令到内存注册表。是"尽力而为"的沙箱——只给受限 api 对象（app/fs/events/log），不隔离 window 访问。
  - **process 插件**（Python）：Rust 用 `std::process::Command` 启动子进程，通过 **JSON-RPC 2.0 over stdio（NDJSON）** 通信——每行一个 JSON，`init` 握手返回插件声明的命令列表，之后按 id 调命令。
- **清单（plugin.json）**：`{ id, name, version, runtime, entry|command, permissions, config }`——权限字段决定插件能否调用核心 API（fs 读写、日志）。
- **生命周期**：发现（扫描 vault/plugins/*）→ 启用（持久化到 `.toolbox/plugins.json`）→ 启动/加载 → 调用 → 崩溃自动重启（限次）→ 禁用/卸载。

### 3.5 网络与服务器
- **reqwest（blocking + rustls）**：AI 对话的 HTTP 客户端。用 `OnceLock` 缓存共享 client（连接复用，避免每次新建）。
- **tiny_http**：博客预览的本地静态服务器（随机端口），返回渲染好的 HTML。
- **pulldown-cmark**：Rust 的 Markdown 解析器，博客生成时把 Markdown 渲染成 HTML（与前端 Vditor 的 Lute 各管一摊）。

## 4. 核心概念（项目里的"黑话"）

### 4.1 Vault（工作区）
- **来源**：Obsidian 的术语，指"一个文件夹 = 一个知识库"。
- **本项目含义**：用户选择的任意文件夹，应用内所有数据（笔记/清单/记录/插件/博客/项目）都放里面：
  ```
  vault/
  ├── notes/            # 笔记（Markdown，可子文件夹）
  ├── projects/         # 项目文件（M8 规划中）
  ├── data/             # 清单 checklists/*.json、记录 records/*.json
  ├── plugins/          # 插件（plugin.json + 入口文件）
  ├── site/             # 博客生成输出
  └── .toolbox/         # 应用设置（如启用的插件列表）
  ```
- **为什么设计成 vault**：数据与代码分离、可 git、可备份、可迁移；换电脑 = 复制文件夹。

### 4.2 纯文件优先（File-First）
- 一切皆文件，不做私有数据库。
- 优点：透明（用记事本就能看数据）、可版本管理、无锁定（不怕应用崩溃丢数据）。
- 代价：搜索/索引需要自己实现（当前是遍历+字符串匹配，大库可换 FTS——见 Backlog）。

### 4.3 Frontmatter（文件头元数据）
- Markdown 文件顶部的 `---` 包裹的 YAML 键值对：
  ```markdown
  ---
  title: 我的文章
  status: published
  tags: 工作, 随笔
  date: 2026-08-01
  ---
  正文……
  ```
- 项目用 `core/blogfm.ts`（前端）和 `core/blog.rs`（后端）各自解析一份（保持 CRLF 兼容）。
- 用途：博客发布（status/title/tags/date）、后续 AI 整理的素材。

### 4.4 双向链接与反链（Backlinks）
- 笔记里写 `[[其他笔记]]`（或清单/记录里引用笔记路径）→ 系统能找出"谁引用了当前笔记"。
- 项目实现（core/records.tsx、Backlinks.tsx）：**精确路径匹配优先，无精确匹配时按 basename 兜底**（避免同名笔记误报）。
- 这是笔记软件"知识网络"的基础能力。

### 4.5 即时渲染（IR，见 2.4）

### 4.6 JSON-RPC 2.0 与 NDJSON
- **JSON-RPC 2.0**：远程调用协议，请求 `{ jsonrpc: "2.0", id, method, params }`，响应 `{ id, result|error }`。
- **NDJSON**（Newline-Delimited JSON）：每行一个 JSON 对象，天然适合流式 stdin/stdout 通信。
- 组合：Python 插件 = 一个循环"读一行 → 处理 → 写一行"，协议简单到任何语言都能实现（这就是"以后支持 Lua/Go"的落点）。

### 4.7 全文搜索（当前实现与局限）
- 当前：递归遍历 `notes/`，文件名匹配优先，正文用 `to_lowercase().contains()` 匹配，每文件限读 256KB。
- 局限：无分词、无索引、大库会慢。
- 演进方向（Backlog）：SQLite FTS5 或 tantivy 建索引，可增量更新。

### 4.8 SSG（静态站点生成）与 Zola 兼容
- 博客不是动态网站，而是"生成静态 HTML"：`blog_generate` 读取笔记 → 渲染 HTML → 输出到 `site/public/`，部署到任意静态托管即可。
- **Zola 兼容**：同时生成 `site/content/`（Markdown 源）+ `config.toml`，以后想换 Zola 框架直接消费这些源文件，不被锁定。

### 4.9 主题系统与设计令牌（Design Tokens）
- 设计令牌：把颜色/间距/字体等设计决策抽成 CSS 变量（`styles/tokens.css`），组件只引用变量不写死值。
- 主题 = 一套令牌覆盖：`ThemeDef { id, name, base, tokens }`，切换时设置 `data-theme` 属性 + 注入 `<style>` 覆盖变量。
- 内置 3 主题（亮/暗/暖）+ 自定义主题编辑器（实时预览，localStorage 持久化）。

### 4.10 本地优先（Local-First）与迁移
- 应用状态存 localStorage（布局偏好、主题），业务数据存文件，配置存 `%APPDATA%/com.toolbox.desktop/`（vault 路径、AI 配置）。
- 数据布局演进时写**自动迁移**（如笔记移到 notes/ 时把旧根目录 .md 搬进去），保证老用户升级不丢数据。

## 5. 开发与调试链路

- **?mock=1 浏览器模式**：不带 Tauri 也能在普通浏览器跑整个前端（用内置示例数据替换 IPC 调用），适合快速调 UI。实现：`isMock` 判断 + 各 Provider 里 mock 分支。
- **CDP（Chrome DevTools Protocol）**：WebView2 是 Chromium 内核，暴露 CDP 端口后可以用 WebSocket 发命令（`Runtime.evaluate` 执行 JS、`Page.captureScreenshot` 截图、`Emulation.setDeviceMetricsOverride` 模拟窗口尺寸）。
- **E2E 流程**（scripts/cdp-*.mjs）：临时在 tauri.conf.json 加 `--remote-debugging-port=9226` → `pnpm tauri dev` → CDP 脚本驱动真实窗口做断言。**这是"真实验证"的标准手段**——mock 测不到的（真实文件系统、真实进程、真实 WebView2）它都能测。
- **控制台转发**：前端 `console.error` 通过 `log_console` 命令转发到 Rust 终端，方便看前端报错。

## 6. 学习路线建议

1. **先读本文档第 1 节**建立架构图，再对照 `docs/操作手册.md` 的目录树走一遍代码。
2. **前端**：从 `src/App.tsx`（组件如何组织）→ `src/core/vault.tsx`（状态层怎么设计）→ 任意一个视图组件（如 NotesView）看"状态层 ↔ 视图层"如何联动。
3. **Rust**：从 `src-tauri/src/lib.rs`（命令注册全景）→ `core/notes.rs`（最简单的文件命令）→ `core/ai.rs`（async + HTTP）→ `plugins/`（最复杂：状态机 + 进程管理）。
4. **概念深化**：Vault/纯文件优先 → Frontmatter → 插件协议（JSON-RPC/NDJSON）→ 主题令牌 → SSG。
5. **动手实验**：`pnpm dev` + 浏览器开 `?mock=1` 改 UI；写一个自己的 webview 插件（照着 `plugins/text-stats/` 抄）；加一个 `#[tauri::command]` 并在 api.ts 里封装。
6. 遇到 Rust 报错先看 `cargo test` / `cargo check` 输出；前端类型错误看 `pnpm build`（tsc）输出。

| Frontmatter | Markdown 顶部的 `---` 元数据块（YAML） |

| Design Token | 把设计决策（颜色/间距）抽成变量 |
| CDP | Chrome DevTools 协议，用于自动化驱动浏览器/WebView |
| Serde | Rust 的序列化/反序列化库 |
| OnceLock | Rust 的"只初始化一次"的全局容器 |
