# ToolBox 第三方插件开发指南

> 适用对象：想为 ToolBox 写插件的开发者（不要求读过宿主源码）。
> 三种运行时全覆盖：**webview（TS/JS，跑在界面内）**、**process（Python 等任意语言，独立子进程）**、
> **native（Rust 编译的 DLL，宿主进程内 FFI）**。
> 读完本文你能独立完成三种插件的开发、构建、打包、安装与调试。
>
> 仓库内可直接对照的完整示例（**每种运行时只保留一个典型**）：
> `plugins/py-tools`（process：协议 + 事件 + 搜索提供者 + 自带前端界面 + 依赖安装，唯一 process 示例）、
> **`core-plugins/example`（native + 自带前端，全部实现要点，配套教程
> [docs/核心插件示例教程.md](核心插件示例教程.md)）**；
> 真实算法型 native 示例见 **`core-plugins/probe-rat-layer`**（探针卡分层，含后台任务/进度/结果页，
> 见 [docs/改造方案-探针卡分层Rust化.md](改造方案-探针卡分层Rust化.md)）；
> webview 插件的最小示例见 §1（hello-tb，几分钟跑通）。
> 皮肤插件示例（纯数据包）见 `plugins/theme-maple`、`plugins/theme-midnight`。

## 0. 插件系统总览

### 0.1 三种运行时怎么选

> 想给软件换皮（主题/皮肤）→ 直接看 **§6 皮肤插件**：声明 `theme` 字段的纯数据包，
> 不用写任何代码逻辑、不需要运行时入口。

| 维度 | webview（TS/JS） | process（Python 等） | native（Rust cdylib DLL） |
|---|---|---|---|
| 运行位置 | 宿主 WebView 界面内 | 独立子进程 | 宿主进程内（FFI，libloading） |
| 通信方式 | 前端 API 对象（同进程） | JSON-RPC over stdio（NDJSON） | C ABI 函数指针 |
| 性能 | 快（同进程） | 慢（进程间 IPC，毫秒级） | 最快（微秒级） |
| 界面能力 | ✅ 可注册命令 / 自带前端 | ❌ 无界面（数据/逻辑型） | ✅ 可带自带前端（Vue 3 IIFE） |
| 第三方库 | npm 依赖在**构建时**打进单文件 | pip 包（vendored / venv，见 §3.5） | Cargo 依赖编译进 DLL |
| 语言要求 | 浏览器 JS/TS | 任意语言（实现协议即可） | Rust（用 tb-sdk） |
| 文件/系统能力 | 仅 `api.fs`（工作区内） | 核心 API（工作区内，权限门控） | 完整（自己用 `resolve_safe`） |
| 崩溃隔离 | 同窗口，报错不崩宿主 | 子进程崩溃自动重启（限次） | panic 经 catch_unwind 隔离 |

**决策建议**：
- 界面 + 轻逻辑 → **webview**（默认推荐，无需任何运行时）；
- 数据处理 / 调第三方库 / 任意语言（Node、PowerShell…）→ **process**；
- 性能敏感、需要完整文件/网络/系统能力、要"编译型工具" → **native（Rust DLL）**。

### 0.2 插件目录与部署

插件安装根**默认**为 `%APPDATA%\com.toolbox.desktop\plugins\`（全局，与工作区无关）；
插件页顶部可**自定义目录**（更改时现有插件自动迁移，旧目录进回收站），恢复默认随时可回。

```
<插件安装根>\                                ← 默认 %APPDATA%\com.toolbox.desktop\plugins\
├── <插件id>\                                  ← 外部插件（webview / process / 主题皮肤）：一个插件一个目录
│   ├── plugin.json                            ← 清单（必填）
│   ├── main.js / main.py / ...                ← 入口（webview / process）
│   └── ui\                                    ← 可选：自带前端（构建产物，见 §2.3）
└── _core\                                     ← 原生插件容器（native）
    ├── core-notes\                            ← 随应用分发的核心插件（打包时部署，可卸载/恢复）
    └── <第三方DLL插件id>\                      ← UI 安装或手动放入的 DLL 插件（见 §4.6）
```

- **webview / process / 主题皮肤插件**：把插件目录复制进安装根即完成安装（或插件页
  「安装目录」一键部署）。插件页点"刷新"即可发现；目录增删/清单变化也会自动触发重新发现。
- **native（DLL）插件**：不能直接丢进安装根（宿主会拒绝加载，见 §0.4）。
  两种合法路径：① 插件页"安装 .zip / 安装目录"（按清单 runtime 自动部署，native → `_core\<id>`）；
  ② 手动放进 `_core\<id>\`（dev 构建也保留手动放入的插件，不会清理）。
- **启用状态**存在 `%APPDATA%\com.toolbox.desktop\plugins.json`（`{enabled:[...]}`），与工作区无关；
  **分享/下载的 vault 不会自动执行其中的插件**。
- 随应用分发的核心插件（native，教学基线 = `core-example`）默认启用、可禁用、可**真实卸载**
  （卸载后记入 `removed_core`，可从插件页一键恢复；开发模式 `pnpm build:core` 重新部署）。
  新核心插件照 `core-plugins/example` 写（见 [docs/核心插件示例教程.md](核心插件示例教程.md)）。

### 0.3 清单（plugin.json）字段

```json
{
  "id": "my-tool",
  "name": "我的工具",
  "version": "0.1.0",
  "description": "一句话说明",
  "runtime": "webview | process | native",
  "entry": "main.js",                 // webview 必填：入口 JS（相对插件目录）
  "command": ["python", "main.py"],   // process 必填：启动命令 argv；native 必填：DLL 文件名
  "permissions": ["fs:read:vault", "fs:write:vault", "log"],
  "config": {},
  "searchProvider": false,            // true = 实现 search.provide 命令，进入全局搜索（§5）
  "system": false,                    // true = 数据安全/横切能力，前端不可禁用（核心插件才用）
  "ui": { "entry": "ui/index.js" },   // 可选：自带前端（§2.3）
  "nav": [{ "id": "my", "label": "我的工具", "icon": "puzzle", "group": "工作区" }],
  "actions": [{ "id": "greet", "label": "示例问候", "icon": "puzzle", "topbar": true, "tray": true }],  // 可选：宿主外壳动作（§7.1）
  "settings": { "entry": "ui/settings.js" },  // 可选：设置页插件段（§7.2）
  "theme": { "base": "light", "tokens": {}, "css": "theme.css" }  // 可选：皮肤插件（§6，纯数据无需 entry）
}
```

- **id 规则**：小写字母/数字开头，仅含小写字母/数字/`-`（`_` 仅内部目录用）；**必须等于目录名**。
- 已知权限：`fs:read:vault`（读工作区内文件）、`fs:write:vault`（写工作区内文件）、`log`（日志）。
  未知权限只警告不阻止加载；**process 插件调核心 API 时按此门控**（§3.3）。
- `nav` 里的 `view` 字段是宿主内置视图名，第三方插件**不写**（点击后自动路由到本插件的
  自带前端 `ui`，见 §2.3 的加载机制）。
- `float`（可选）：桌面浮窗界面入口（如 `"float": { "entry": "ui/float.js" }`）。插件启用且
  声明后，**桌面半透明浮窗（Alt+Q）显示该插件界面**（注册 key = 插件 id，与主界面同机制）；
  多个插件声明时浮窗底部页签切换；不声明则浮窗显示空态。入口独立于 `ui`（浮窗可做精简版，
  如 core-example 的 `ui/float.ts`）。浮窗窗口能力（创建/置底/快捷键/锁定）属宿主框架。

### 0.4 安全模型与能力边界（重要）

> **核心结论：本应用是「单用户、插件主动安装」模型——真正的安全边界是"你是否信任并主动安装了这个插件"，
> 而不是代码签名或沙箱。** 若未来引入第三方插件市场，必须补代码签名 / 系统级沙箱。

- **webview**：JS 与宿主**同源同权**，经 Blob URL `<script>` 注入后可 `invoke` 全部 Tauri 命令
  （含读写 vault、安装/卸载插件、切换插件目录等）。`permissions` 声明**不限制 webview 运行时**
  （目前仅 process 运行时消费）。桥（`api.call` / `api.on` / `api.context`）只是便利封装，**不是安全边界**。
  安装任意 webview 插件 ≈ 授予应用全部能力。
- **process**：子进程边界提供**崩溃/挂死隔离**（崩溃自动重启、超时杀进程），但**不是安全沙箱**——
  插件进程可做任意 OS 操作（写任意路径、联网、读环境变量）。`permissions` 只门控"经宿主转发的核心 API"
  （`fs.readText` / `fs.writeText` / `log` 等），拦不住插件自身行为。
- **native（DLL）**：DLL 被加载进宿主进程 = 完全控制（进程内任意代码执行）。加载位置限制在 `_core`
  容器下（`plugins\` 根下的 native 目录拒绝启动，见 §4.1）。**注意**：UI 安装会把用户选择的任意 zip
  （声明 `runtime: "native"`）部署进 `_core` 并以完全信任加载——「native = 随应用分发的信任代码」这一
  直觉在 UI 安装路径下不成立，native 信任实际来自「用户主动安装」这一动作，只安装可信来源的插件。
- 插件安装包解压带 zip-slip 防护（拒绝 `../` 越界路径），id 白名单校验（防路径穿越）。
  所有带 `vault` 参数的命令都会校验"必须等于已配置的工作区"（S1c），防止把文件作用域指向任意目录。

### 0.5 开发环境与工作流

```bash
# 仓库根（本指南面向"独立开发"，也可不在仓库里开发）
pnpm sync:plugins          # 把仓库 plugins/ 下的外部插件同步到 %APPDATA%（开发时改代码后跑）
pnpm build-external-ui plugins/<id>   # 构建外部插件的自带前端（ui/index.tsx → ui/index.js）
pnpm tauri dev             # 启动应用（dev 终端可见插件日志）
```

> 不在仓库里开发也没关系：直接改 `%APPDATA%\com.toolbox.desktop\plugins\<id>\` 里的副本，
> 在插件页点"重载"（process/native）或刷新页面（webview 命令重载）即可生效。
> process 插件进程常驻：改 Python 代码后需要"重载"或重启应用。

### 0.6 仓库外开发第三方插件（推荐：独立模板）

第三方插件**不必在本仓库里开发**——推荐直接用仓库自带的独立模板
[`templates/external-plugin/`](../templates/external-plugin/)（Python 进程 + Vue
自带前端，含 `package.json`/`build.mjs`，**自带构建脚本、不依赖 ToolBox 仓库**）：

```bash
# 1. 复制模板并改名（插件目录名 = 插件 id；id 规则：小写字母/数字开头，仅含小写字母/数字/连字符）
cp -r templates/external-plugin my-tool
# 2. 改 plugin.json 的 id/name/nav，并把 ui/index.ts 的注册 key 改成你的 id
# 3. 装依赖 + 构建前端（产物 ui/index.js + style.css 本地生成，不入库）
cd my-tool && npm install && npm run build
# 4. 装进 ToolBox（二选一）
#    ① 插件页「安装目录」选本目录，或「安装 .zip」（压缩包顶层含 plugin.json 或 <id>/plugin.json）
#    ② 把整个目录复制到应用插件目录（默认 %APPDATA%\com.toolbox.desktop\plugins\）后点「刷新」
```

**第三方插件目录结构**（自包含，整个目录即一个插件）：

```
my-tool/
├── plugin.json       # id/name/runtime/command/permissions/ui/nav/config
├── main.py           # Python 进程（JSON-RPC 协议，见 §3）；也可换 node/任意语言
├── requirements.txt  # 可选：第三方依赖声明（插件页「安装依赖」按钮装到 vendor/）
├── build.mjs         # 前端构建脚本（vite lib，照抄仓库 scripts/plugin-ui-build.mjs）
├── package.json      # 构建依赖（vue/vite/@vitejs/plugin-vue，独立 npm install）
└── ui/               # 自带前端：index.ts + App.vue + bridge.ts（构建产物 index.js/style.css）
```

要点：

- **构建产物不入库**：`ui/index.js`、`ui/style.css`、`vendor/`、`env/`、`.venv/` 都是
  本地生成物——分发/分享源码（plugin.json + main.py + ui/*.ts|vue + requirements.txt），
  对方装好后点「安装依赖」补依赖、重载生效。
- **界面样式**：写在 `.vue` 的 `<style>` 块（构建时 Vite 提取为 ui/style.css，宿主注入），
  只引用宿主设计令牌（`--bg/--fg/--accent/--space-*/--radius-*`），随亮暗主题自适应；
  类名用自己的前缀避免污染宿主。**不要写独立未 import 的 style.css**（构建链路不带，界面裸奔）。
- **界面与 Python 通信**：`api.call("hello")` → 宿主 JSON-RPC 调 `hello` 命令；
  Python `notify("progress", {...})` → 界面 `api.on("progress")`。详见 §3.8。
- **分发（两种方式）**：
  - 应用内：插件页「导出」打包 zip 分享，对方插件页「安装 .zip」即装（含依赖目录，包大）。
  - 作者侧：`pnpm package-plugin <插件目录> [-o 输出.zip]`——自动排除
    `vendor/env/.venv/node_modules/__pycache__` 等依赖/缓存目录（对方装好后点「安装依赖」
    重建），包更小；产物顶层 = `<插件id>/`，与应用内导出/安装布局一致。仓库外开发的插件
    也可用（脚本在仓库 `scripts/package-plugin.mjs`，或照抄逻辑）。
- **独立测试（不启动 ToolBox）**：模板自带 `test/mock-host.py`（process 协议冒烟：
  init + 白名单命令逐条 call + 事件数校验 + 核心 API 模拟应答）与 `npm test`
  （前端：入口契约 + App.vue 行为，api 全 mock）——开发循环里先独立测、再装进宿主
  冒烟，详见模板 DEVELOPER.md §12。
- **开发循环**：改 Python → 插件页「重新加载」；改前端 → `npm run build` 后再重载。

## 1. 五分钟跑通：最小 webview 插件

> 仓库已含本示例实体：`plugins/hello-tb/`（plugin.json + main.js，可直接对照/安装）。

```bash
mkdir %APPDATA%\com.toolbox.desktop\plugins\hello-tb
```

`plugin.json`：

```json
{
  "id": "hello-tb",
  "name": "打招呼",
  "version": "0.1.0",
  "description": "最小示例：注册一个 sayHello 命令",
  "runtime": "webview",
  "entry": "main.js",
  "permissions": []
}
```

`main.js`：

```js
api.app.registerCommand({
  id: "sayHello",
  name: "打招呼",
  run: async (args) => ({ text: `你好，${args?.name || "世界"}！` }),
});
```

启动应用 → 插件页出现"hello-tb" → 启用 → 命令列表出现 `sayHello` → "命令试用台"填
`{"name":"小明"}` 调用，返回 `{"text":"你好，小明！"}`。完成。

## 2. webview 插件（TS/JS）详解

跑在宿主 WebView 界面内（浏览器 JS 引擎），**没有 Node 运行时**。两种形态可同时用：
命令注册式（无界面）与自带前端（有界面）。

### 2.1 命令注册式入口（main.js / main.ts）

入口文件顶层会收到一个全局 `api` 对象（宿主按插件独立注入，见 §2.2）。最小示例：

```js
api.app.registerCommand({
  id: "analyze",            // 命令 id（插件内唯一）
  name: "统计文本",          // 展示名（插件页命令试用台可见）
  run: async (args) => {    // args 是调用方传入的 JSON 对象
    const text = typeof args?.text === "string" ? args.text : "";
    const trimmed = text.trim();
    return {
      chars: [...text].length,
      words: trimmed ? trimmed.split(/\s+/).length : 0,
      lines: text.length === 0 ? 0 : text.split("\n").length,
      paragraphs: trimmed ? trimmed.split(/\n\s*\n/).length : 0,
    };
  },
});
```

**用 TS 写入口**：源码写 `main.ts`，构建时打成单文件 `main.js`：

```bash
npx esbuild main.ts --bundle --outfile=main.js --format=iife
```

> 打包版 CSP 会拦截 `eval` / `new Function`——**不要**在入口里用它们；宿主加载用的是
> Blob URL `<script>` 注入（CSP `script-src blob:` 允许），入口必须是普通脚本文件。

### 2.2 api 对象全字段

入口顶层直接可用的 `api`（由宿主 `src/core/plugins.tsx` 构造；字段与"插件自带前端"的
统一桥一致，见 §2.3）：

| 成员 | 说明 |
|---|---|
| `api.app.registerCommand({id, name, run})` | 注册命令（本插件的命令在此声明） |
| `api.fs.readText(rel)` / `api.fs.writeText(rel, content)` | 读写**工作区内**文件（vault 相对路径，`/` 分隔；越界被拒） |
| `api.events.on(event, cb)` / `api.events.emit(event, data)` | 插件内事件（本插件各入口间互通） |
| `api.log(...args)` | 打日志（dev 终端可见，前缀 `[plugin:<id>]`） |
| `api.call(command, args?, targetPluginId?)` | **调用插件命令**：默认本插件；传 `targetPluginId` 跨插件调用 native/process 插件 |
| `api.on(event, cb, targetPluginId?)` | 订阅 `plugin-event`（默认本插件；跨插件传第三个参数），返回取消函数 |
| `api.context` | 宿主注入上下文：`{ vault: 当前工作区路径, activePath?, activeContent? }` 等 |

**跨插件调用示例**（webview 插件调用 process 插件的命令）：

```js
const r = await api.call("pytext.stats", { text: "你好 world" }, "py-tools");
```

**事件订阅示例**（订阅 py-tools 推送的 progress 事件）：

```js
const off = api.on("progress", (data) => console.log("进度:", data));
// 不再需要时 off() 取消
```

### 2.3 自带前端（组件模式，有界面的插件推荐）

插件目录放一份自包含的 Vue 3 产物，宿主把它挂载到自己的界面里（**非 iframe**，宿主全局
CSS/主题直接生效）。native 核心插件全部用此模式（样板见 `core-plugins/example` +
[docs/核心插件示例教程.md](核心插件示例教程.md)）；外部插件同样支持（构建：
`pnpm build-external-ui plugins/<插件>` 生成 ui/index.js）。

```
<插件id>\
├── plugin.json          # 声明 "ui": { "entry": "ui/index.js" }
└── ui\
    ├── index.ts         # 入口：createApp 挂载 + 注册 __TB_PLUGIN_UI__
    ├── App.vue          # 主组件（宿主注入 api 桥为 props）
    ├── bridge.ts        # 可选：PluginBridgeApi 类型（只声明用到的方法）
    ├── index.js         # 构建产物：自包含 IIFE（Vue 打进产物）
    └── style.css        # 可选：插件样式（Vite 提取）
```

**ui/index.ts 入口骨架**：

```ts
import { createApp, type App as VueApp } from "vue";
import App from "./App.vue";

/** 宿主注入的桥 API（完整字段见 src/core/pluginRuntime.ts） */
interface PluginBridgeApi {
  pluginId: string;
  call: (command: string, args?: unknown, targetPluginId?: string) => Promise<unknown>;
  on: (event: string, cb: (data: unknown) => void, targetPluginId?: string) => () => void;
  context: { vault: string | null } & Record<string, unknown>;
  nav?: { go: (view: string) => void; openNote: (rel: string) => void };
  host?: { search: (query: string) => Promise<unknown[]> };
}

declare global {
  interface Window {
    __TB_PLUGIN_UI__?: Record<
      string,
      { mount: (el: HTMLElement, api: PluginBridgeApi) => void; unmount?: () => void }
    >;
  }
}

let app: VueApp | null = null;
window.__TB_PLUGIN_UI__ = window.__TB_PLUGIN_UI__ || {};
window.__TB_PLUGIN_UI__["my-tool"] = {
  mount(el, api) {
    app = createApp(App, { api });
    app.mount(el);
  },
  unmount() {
    app?.unmount();
    app = null;
  },
};
```

**ui/App.vue 主组件**：

```vue
<script setup lang="ts">
import { ref } from "vue";

const props = defineProps<{ api: PluginBridgeApi }>();
const text = ref("");

const run = async () => {
  // 例：调用 py-tools 的统计命令（跨插件）
  const r = (await props.api.call("pytext.stats", { text: text.value }, "py-tools")) as {
    words: number;
  };

</script>

<template>
  <!-- 复用宿主全局 CSS class（.card / .btn 等）即可随主题自适应 -->

  </div>

```

```bash

```

脚本（`scripts/build-external-ui.mjs`）做三件事：Vite lib 模式打 IIFE（Vue 打进产物）、产物写回
`<插件目录>/ui/`（index.js + style.css）。不在仓库开发时照抄该脚本的内联 vite 配置即可。

**加载机制**：宿主 `PluginUiView` 经 `plugins_read_file` 读 `ui/index.js` → Blob URL `<script>`
注入（CSP 允许）→ 插件顶层注册 `window.__TB_PLUGIN_UI__[id]` → 宿主注入 api 桥，插件
`createApp(App, { api }).mount(el)` 挂载。`nav` 声明了入口的插件，侧边栏点击即进入本界面；
`api.nav.go(view)` 可跳回宿主其他视图。

## 3. process 插件（Python 等任意语言）详解

独立子进程 + **JSON-RPC 2.0 over stdio（NDJSON：每行一个 JSON 对象）**。
最小协议骨架照抄模板 `templates/external-plugin/main.py`；仓库内完整示例 =
`plugins/py-tools`（协议 + 第三方库 + 事件 + 搜索提供者 + 自带前端）。

### 3.1 协议（完整形态）

```
宿主 → 插件   {"id": 1, "method": "init",  "params": {"apiVersion": 1, "pluginId": "py-tools"}}
插件 → 宿主   {"id": 1, "result": {"commands": ["pytext.stats", "pytext.humanDate", "pytext.eventDemo", "search.provide"]}}
宿主 → 插件   {"id": 2, "method": "call",  "params": {"command": "pytext.stats", "args": {...}}}
插件 → 宿主   {"id": 2, "result": {...}}                     # 成功
插件 → 宿主   {"id": 2, "error": {"code": -32000, "message": "..."}}   # 失败
插件 → 宿主   {"method": "progress", "params": {...}}         # Notification：事件推送（无 id）
插件 → 宿主   {"id": 3, "method": "fs.readText", "params": {"path": "notes/a.md"}}  # 调用核心 API
宿主 → 插件   {"id": 3, "result": "文件内容"}
宿主 → 插件   {"method": "shutdown"}                          # 关闭信号（无 id）
```

要点：
- **启动**：`command[0]` 为可执行程序，`command[1..]` 为参数；**cwd = 插件目录**（脚本可用相对路径）。
  对 `python` / `python3`，宿主按 **三级解析** 替换解释器（见 §3.5）：插件目录自带 `python.exe` →
  全局捆绑运行时 → 系统 PATH。目标机没有 Python 也能跑（应用随包分发运行时）。
- **生命周期**：spawn → `init` 握手（响应里的 `commands` 数组即插件声明的命令白名单，未声明的
  命令宿主拒绝调用）→ ready →（`call` / 事件 / 核心 API）* → `shutdown`。
- **健壮性**（宿主侧保证）：调用超时 30s（挂死自动终止进程树）、崩溃自动重启（60s 窗口内限 3 次）、
  单行 > 8MB 丢弃、非法 UTF-8 按 lossy 处理不误判退出、stderr 捕获（转发日志 + 保留末尾，
  init 失败时回显 Python traceback 便于定位缺依赖）。
- **UTF-8 强制**：Windows 下管道默认 ANSI 代码页（GBK），Python 必须 `reconfigure(encoding="utf-8")`，
  否则中文 JSON 会乱码/崩溃（py-tools / 模板 main.py 里已示范）。

### 3.2 最小 main.py（照抄模板 `templates/external-plugin/main.py` 结构；py-tools 为完整版）

```python
#!/usr/bin/env python3
"""JSON-RPC over stdio（NDJSON）插件。核心约定了 3 种入站消息与 2 种出站消息。"""
import json
import sys

def handle_request(msg):
    """处理宿主请求（init / call），返回带 id 的响应。"""
    mid = msg.get("id")
    method = msg.get("method", "")
    params = msg.get("params") or {}
    try:
        if method == "init":
            result = {"commands": ["demo.hello"]}          # 声明命令白名单
        elif method == "call":
            command = params.get("command", "")
            args = params.get("args") or {}
            if command == "demo.hello":
                result = {"text": "你好，%s！" % args.get("name", "世界")}
            else:
                raise ValueError("未知命令: %s" % command)
        else:
            raise ValueError("未知方法: %s" % method)
        return {"id": mid, "result": result}
    except Exception as e:                                  # noqa: BLE001
        return {"id": mid, "error": {"code": -32000, "message": str(e)}}

def notify(event, params):
    """向宿主推送事件（Notification，无 id）→ 前端 api.on(event) 收到。"""
    sys.stdout.write(json.dumps({"method": event, "params": params}, ensure_ascii=False) + "\n")
    sys.stdout.flush()

def call_core(method, params):
    """调用核心 API（fs.readText 等，按 plugin.json 的 permissions 放行）。
    注意：只能在处理宿主请求期间调用（宿主在该期间才会响应核心 API 请求）。"""
    sys.stdout.write(json.dumps({"id": 9000, "method": method, "params": params}, ensure_ascii=False) + "\n")
    sys.stdout.flush()
    msg = json.loads(sys.stdin.readline())
    if "error" in msg:
        raise ValueError(msg["error"].get("message", "核心 API 错误"))
    return msg.get("result")

def main():
    # Windows 管道强制 UTF-8（否则中文 JSON 乱码）
    for stream in (sys.stdin, sys.stdout):
        try:
            stream.reconfigure(encoding="utf-8")
        except (AttributeError, ValueError):
            pass
    for line in sys.stdin:
        line = line.strip()
        if not line:
            continue
        msg = json.loads(line)
        if msg.get("method") == "shutdown":                 # 宿主关闭信号：及时退出，不要挂起
            break
        if "id" in msg and "method" in msg:
            sys.stdout.write(json.dumps(handle_request(msg), ensure_ascii=False) + "\n")
            sys.stdout.flush()

if __name__ == "__main__":
    main()
```

配套 `plugin.json`：

```json
{
  "id": "demo-py",
  "name": "Python 示例",
  "version": "0.1.0",
  "runtime": "process",
  "command": ["python", "main.py"],
  "permissions": ["fs:read:vault", "log"],
  "config": {}
}
```

### 3.3 核心 API（按权限放行）

| 方法 | 所需权限 | 说明 |
|---|---|---|
| `fs.readText` | `fs:read:vault` | 读工作区内文件。参数 `{path}`：vault 相对路径（`/` 分隔）；`..`/绝对路径/盘符越界被拒 |
| `fs.writeText` | `fs:write:vault` | 写工作区内文件。参数 `{path, content}`；父目录自动创建 |
| `fs.listDir` | `fs:read:vault` | 目录枚举。参数 `{dir}`（空 = vault 根）；返回 `[{name, path, isDir, size, mtime}]`，`path` 为相对路径，`mtime` 为 UNIX 毫秒整数（按最近修改排序用），按 `path` 排序 |
| `log` | `log` | 日志。参数 `{message, level?}`（level: debug/info/warn/error，缺省 info）→ 宿主运行日志（logs/ 落盘 + dev 终端）`[plugin:<id>] ...` |
| `notify` | `notify` | 通知：宿主 UI 右上角横幅（plugin-event `notification` 事件）。参数 `{title, body}`；应用最小化时横幅不可见 |
| `open` | `open` | 默认应用打开 vault 内文件。参数 `{path}`（vault 相对路径） |
| `clipboard.read` / `clipboard.write` | `clipboard` | 剪贴板文本读写。read 无参返回文本；write 参数 `{text}` |
| `http.request` | `http` | 受控 HTTP 请求（宿主侧 reqwest，超时 + 响应 4MB 上限）。参数 `{url, method?, headers?, body?, timeoutSec?}`；返回 `{status, headers, text}` |
| `shell.exec` | `shell` | 执行命令（**强能力**，cwd = 插件目录，超时 + 输出尾部 40 行）。参数 `{cmd, args?, timeoutSec?}`；返回 `{code, stdout, stderr}` |

> 权限一律在 `plugin.json` 的 `permissions` 声明才可用；未知权限只警告不阻止加载。
> 示例：`plugins/py-tools` 演示核心 API 调用（`call_core("fs.listDir", ...)` 列文件、
> 界面经 api.call 调命令）；完整核心 API 清单与权限见上表。

**任何语言**只要实现"读 stdin 一行 JSON、写 stdout 一行 JSON"即可成为插件
（Node / PowerShell / Go / …同理，见 §3.7）。

### 3.4 事件推送

插件在**处理命令期间**（或后台线程）向 stdout 写 Notification 行即可推送事件：

```python
notify("progress", {"percent": 50, "message": "处理中…"})
```

宿主收到后转发为前端 `plugin-event`（payload `{pluginId, event, data}`）；前端/其他插件用
`api.on("progress", cb)` 订阅（默认只收本插件事件，跨插件传第三个参数）。插件页有实时事件流展示。

> ⚠️ **事件只在 call 在途时转发**（`process.rs` 的 `call_raw` 循环内；`read_loop` 只把
> stdout 解析进通道，空闲期不消费转发）。**后台线程推的事件不会实时到达前端**，会在
> 通道积压、下一次 call 时顺带转发（顺序仍正确，只是延迟）。长任务（>30s 宿主 call 超时）
> 必须走异步模式：call 秒回 jobId → 后台线程跑 → 前端**轮询 status 类命令**驱动进度，
> progress 通知当实时补充。完整实例见 `core-plugins/probe-rat-layer`（native，原 process
> 实例；异步与三层状态模型同样适用，架构说明见其 README）。

### 3.5 解释器与第三方库（两层模型）

**解释器来源（宿主自动解析，目标机无需装 Python）**：宿主对 `command[0]` 为
`python` / `python3` 的插件按三级解析替换解释器：

```
1. 插件目录自带 python.exe（<插件>/python.exe）   ← 插件完全自包含（方案 D）
2. 全局捆绑运行时（%APPDATA%/com.toolbox.desktop/python/） ← 默认路径
3. 系统 PATH 的 python                            ← 原行为兜底
```

全局捆绑运行时 = **python-build-standalone**（uv 内置的同一套可重定位 CPython，不写注册表），
构建期 `pnpm fetch:python` 下载 **full 变体（含 pip）** 到 `src-tauri/resources/python/`，
随安装包分发；打包版首启由宿主部署到配置目录。目标机无 Python、无网络也能跑 Python 插件。

**第三方库放置**（依赖随插件走，插件 = 自包含目录）：

| 方案 | 目录布局 | 适用 |
|---|---|---|
| **A. 插件目录 vendored（推荐）** | `<插件>/vendor/`，`pip install --target vendor <pkg>`（构建机或目标机插件页「安装依赖」按钮：插件带 `requirements.txt` 时用捆绑 Python 的 pip 一键装到 vendor/）；代码 `sys.path.insert(0, os.path.join(os.path.dirname(__file__), "vendor"))` | 插件自包含、卸载即净、离线可跑；py-tools 即此方案 |
| **B. 插件自带 site-packages** | `<插件>/env/`，启动时把 `env` 插进 `sys.path` | 二进制 wheel（pandas 等）；wheel 的 ABI 必须匹配捆绑/系统解释器版本（cp313/cp314） |
| **C. 插件内 venv** | `<插件>/.venv/`，command 用 `.venv/Scripts/python.exe`（Windows） | 依赖隔离干净，但目录大、首次需安装 |
| **D. 自带整个运行时** | `<插件>/python.exe` + 依赖（解压 python-build-standalone 进插件目录） | 必须锁死 Python 小版本行为差异；+15~25MB/插件（宿主解析优先级最高，见上） |
| ~~系统 Python + pip~~ | ~~`pip install x`（装进系统 site-packages）~~ | 已被全局捆绑运行时取代（目标机不再依赖系统 Python） |

> cwd = 插件目录，`Path(__file__).parent` 即可定位插件内任意资源（如读取同目录的数据文件）。
> 依赖必须是纯 Python 或与捆绑解释器 ABI 匹配的 Windows x86_64 wheel；禁止需要目标机现场编译的包。

> **「安装依赖」按钮会先停掉该插件进程再跑 pip，装完后由前端自动重新加载**——正在运行的
> 插件进程与 pip 并发读写同一批 vendor 文件时，Windows 文件锁会让新进程 import 读被拒
> （`PermissionError: [Errno 13] Permission denied: ...\vendor\jmespath\__init__.py`，实测踩过）。
> 方案 C（`.venv/Scripts/python.exe` 作为 command）的插件**不要**声明 requirements.txt，
> 否则按钮会把依赖装到 vendor/（错误位置）；且 .venv 未创建时启动会失败，报错会提示
> "解释器文件不存在"，先按方案 C 的创建步骤初始化 .venv 再启用。

### 3.6 搜索提供者（searchProvider）

来源以 `source: <插件id>` 字段标记，前端展示徽章）。契约见 §5，完整示例见

### 3.7 其他语言 / Node

**Node 当执行器**（想要完整 npm 生态 / fs / path）：

```json
{ "runtime": "process", "command": ["node", "main.js"], "permissions": ["fs:read:vault"] }
```

`node_modules` 放插件目录即可（cwd = 插件目录，Node 标准解析）。协议同 §3.1——写

### 3.8 process 插件加自带前端（界面 / 子页，Python 插件推荐）

**任何 runtime（webview / process / native）都能带界面**：manifest 声明 `ui` + `nav` 后，
宿主侧边栏出现入口、插件页卡片出现「打开」按钮，点击进入 **PluginUiView**（宿主窗口内
挂载，非 iframe，复用宿主全局 CSS/主题）。界面与 Python 子进程经统一桥通信：
`api.call` → `plugin_call` → 宿主路由为 JSON-RPC（stdin/stdout），`api.on` 订阅插件
推送的事件——**界面代码（TS/Vue）与后端代码（Python）完全解耦，各写各的**。

仓库完整示例：`plugins/py-tools/`（ui/ 目录 + plugin.json 的 `ui`/`nav` 声明，
界面三个卡片分别调 `pytext.stats` / `pytext.humanDate` / `pytext.eventDemo`，
并用 `api.on("progress")` 实时收进度事件）。步骤：

1. **plugin.json 声明界面与导航**（process 插件加这两个字段即可，`command` 不变）：

   ```json
   {
     "runtime": "process",
     "command": ["python", "main.py"],
     "ui": { "entry": "ui/index.js" },
     "nav": [{ "id": "py-tools", "label": "文本工具", "icon": "file-text", "group": "插件" }]
   }
   ```

2. **写 ui/ 目录**（与 core-example 同结构，见 §2.3 的骨架）：
   `index.ts`（`createApp(App, { api }).mount(el)` + 注册 `__TB_PLUGIN_UI__["<插件id>"]`）、
   `App.vue`（界面组件，`defineProps<{ api: PluginBridgeApi }>()`）、`bridge.ts`（桥类型）、
   `style.css`（插件私有样式；宿主会自动注入同目录 style.css，无则跳过）。
3. **构建**：`pnpm build-external-ui plugins/<id>` → 产物 `ui/index.js`（自包含 IIFE，
   Vue 打进产物，gitignored）写回插件目录。
4. **生效**：`pnpm sync:plugins`（仓库外开发直接改 %APPDATA% 副本）→ 应用内侧边栏
   「文本工具」进入界面；改 Python 代码后插件页「重新加载」重启进程。

要点：

- **界面调用命令** = 宿主 `plugin_call`，与插件页命令试用台同一条通道；命令白名单是
  init 握手声明的 `commands`，界面调未声明命令会被拒绝。
- **事件实时**：Python 侧 `notify("progress", {...})`（Notification）→ 宿主转发
  `plugin-event` → 界面 `api.on("progress", cb)` 订阅，无需轮询。
- **子页**：一个插件可声明多个 `nav` 项（多个侧边栏入口），都挂载同一个 `ui/index.js`；
  界面内用 `api.nav.go(view)` 跳宿主其他视图。宿主内置路由（overview/plugins/settings）
  不可被插件 nav 占用。
- **注意**：界面代码运行在宿主窗口（WebView），**没有 Node 运行时**——文件能力用
  桥（`api.call` 调 Python 命令，Python 侧再经核心 API `fs.readText` 等）或
  `api.context.vault` 拼路径交给 Python，不要在界面里直接读写文件。

### 3.9 自带前端生命周期与状态恢复（挂载安全）

> 一句话：**宿主会卸载你的界面，但不会杀你的进程——把状态放进程/磁盘，挂载时恢复。**

**宿主行为（所有插件一致，写代码前先接受它）**：切换侧边栏/离开插件页时，宿主
`PluginUiView` 对插件 UI 执行 `unmount()`，**界面内存状态全部丢失**（Vue 组件 ref、
定时器、Map 缓存都没了）；再回来时重新注入 `ui/index.js` 并从头 `mount()`。
因此"页面切走再回来"对任何插件都是**全新挂载**——前端不能假设任何内存状态还在。

但**进程插件本身常驻**（宿主随应用启动拉起、崩溃自动重启，与页面切换无关），
`settings.json` 与磁盘文件也是持久的。要做到"切走再回来不重头开始"，只需遵循
**三层状态模型**（`core-plugins/probe-rat-layer` 是完整实例，native；架构说明见其 README）：

| 状态 | 放哪 | 挂载时怎么恢复 |
|---|---|---|
| 表单/参数 | 进程侧 `settings.json`（`layer.config set`，**防抖 600ms 实时存**，别只在提交时存） | 挂载时 `get` 回填表单 |
| 后台任务 | 进程内存 + **磁盘 `jobs/<id>/meta.json`**（成功时写摘要/输出目录/文件清单，启动时 `_restore_jobs` 扫描恢复） | 挂载时问状态命令（`layer.status`），按 `running`/`done`/`failed` 分支恢复界面 |
| 重资源产物 | 磁盘（SVG/PNG 等渲染缓存按 jobId+kind 落 `jobs/<id>/img/`） | 前端缓存 Map 只是提速层，丢了也无妨——后端磁盘缓存命中秒回 |

**三个硬性约定**（都是这次踩过的坑）：

1. **命令返回字段用 camelCase，且要与前端类型定义逐字对齐**。`layer.status` 曾返回
   snake_case `job_id` 而前端读 `jobId`——永远是 `undefined`，结果页永远恢复不出来，
   用户只能重头开始。JSON-RPC 协议里统一 camelCase（`jobId`/`outDir`/`layerCount`），
   Python 侧 `dict(_ACTIVE)` 这种原样透传最容易踩（键名是 Python 风格）。
2. **状态命令必须幂等可轮询**（`layer.status` 秒回、无副作用）。前端挂载时问一次，
   运行中每 600ms 轮询一次，靠它驱动进度与终态收敛。
3. **恢复态要区分"首次完成"与"恢复"**：完成通知（`layer.notifyDone`）按 jobId 去重
   （`notifiedJobs: Set<string>`），否则每次挂载恢复 done 都重弹横幅。

**给前端的图用 PNG，别用 SVG**（WebView2 上实测）：matplotlib 出 SVG 不难，但
几千条 `<path>` 的 SVG DOM 交给 WebView2 光栅化是"点开图等很久"的隐藏瓶颈——
后端磁盘缓存命中后它秒回数据，慢的是浏览器端重新解析/光栅化。PNG 由 matplotlib
后端光栅化好，浏览器只解码位图，`<img src="data:image/png;base64,...">` 直显
（`data:` 在宿主 CSP `img-src` 白名单内），payload 还更小。CLI/本地仍可保留
SVG（矢量可缩放），**插件界面一律 PNG**。

**webview 插件也一样**：宿主同样卸载/重挂载，但 webview 插件进程归前端自己管，
切走即销毁——它没有常驻进程可依赖，状态只能靠 `settings.json` 类持久化 + 挂载时
回填；process 插件的"进程常驻"是它比 webview 更耐切页的根本原因。

### 3.10 多工作区上下文（TB_WORKSPACE）

宿主 2026-09 起采用**数据根目录模型**：选择一个数据根目录（如 `D:\ToolBoxData`）后，
根下 `Project/` 的**每个直接子文件夹 = 一个工作区**（如 `Project/MG5` 即工作区 MG5），
应用有"当前工作区"（顶栏下拉切换）；每个工作区内自动维护隐藏目录 `.toolbox`
（该工作区的配置/信息存放处，宿主写搜索索引/备份/元数据，插件也可读写）。
process 插件进程启动时，宿主注入环境变量 **`TB_WORKSPACE` = 当前工作区的绝对路径**：

```python
import os
workspace = os.environ.get("TB_WORKSPACE")  # 如 D:/ToolBoxData/Project/MG5
```

- 插件进程在**启动时**拿到的是当时的当前工作区；用户切换工作区后**已运行的插件进程
  不会重启**（环境变量不变）——需要感知切换时，用 `workspace_get` 命令或监听前端
  `workspace-changed` 事件自行处理（前端切换后重新调用插件命令即可，宿主命令层
  始终按**当前**工作区校验）。
- 文件类命令（`fs.*` / `search` / `files_*`）的 `vault` 参数必须等于当前工作区路径，
  否则宿主拒绝（S1c 校验）——插件读文件别自己拼绝对路径，优先走宿主命令。
- 未配置数据根（首启引导页未完成）时应用停留在引导页，插件不会被启用。

#### 文件输入（Inbox，`TB_INBOX`）

宿主另有**文件输入目录** `数据根/Input`（未知/待分类文件的暂存区，插件可**只读**它，
写仍限当前工作区）。process/native 插件启动时宿主注入 `TB_INBOX` = 该目录绝对路径
（似 `TB_WORKSPACE`；未配置数据根时不注入）：

```python
import os
inbox = os.environ.get("TB_INBOX")  # 如 D:/ToolBoxData/Input（可能为 None）
```

- 读取 Inbox 里的文件：`fs.readText`/`fs.listDir` 允许传 **Inbox 内绝对路径**（只读）。
- native 插件经配置 `input_dir` 拿到该路径；其文件浏览在「当前工作区 ∪ Input」内。
- 默认流程：Allegro 等导出文件先拖进「文件输入」视图 → 工作区/插件从 Inbox 读取 →
  处理后再归类（移入工作区）。

## 4. native 插件（Rust DLL）详解

native 插件 = 编译为 **cdylib（Windows .dll）** 的独立 Rust crate，宿主用 **libloading** 加载，
经 5 个 `extern "C"` 导出符号调用。性能定位：FFI 函数调用 + JSON 序列化（微秒级），
是三种运行时里最快的通道。仓库样板：`core-plugins/example`（含自带前端，全部实现要点，
配套教程见 [docs/核心插件示例教程.md](核心插件示例教程.md)）。

### 4.1 能力与安全边界

> ⚠️ **重要**：DLL 加载进宿主进程 = 完全控制宿主（进程内任意代码执行）。位置限制（`_core` 容器）只是
> 防止"意外从 `plugins\` 根加载"，**不是信任边界**——UI 安装会把用户主动选择的任意 native zip 部署进
> `_core` 并加载。只安装你信任来源的 native 插件。

- DLL 加载进宿主进程 = 完全控制宿主。因此宿主只认 `plugins\_core\` 容器下的插件：
  `plugins\` 根下 `runtime: "native"` 的目录会被拒绝启动（提示"不在核心插件目录"）。
- 第三方 DLL 插件两条合法路径：
  1. **插件页「安装 .zip / 安装目录」**（推荐）：选 zip 包或插件目录 → 按清单 runtime 校验并部署
     （native → `_core\<id>`；webview/process/主题 → 安装根，通用安装）→ 默认启用并启动。见 §4.6。
  2. **手动放入** `<插件安装根>\_core\<id>\`（plugin.json + DLL + 可选 ui/）：
     应用会随目录快照变化自动发现。
- 命令调用：宿主 `plugin_call` / 前端 `api.call` 统一路由（native → FFI），与 process 插件
  对前端完全透明。

### 4.2 工程结构

```
my-dll-plugin/
├── Cargo.toml            # [lib] crate-type = ["cdylib"]；依赖 tb-sdk
├── src/
│   └── lib.rs            # 状态类型 + 命令分发 + tb_plugin! 宏（FFI 样板全自动）
└── ui/                   # 可选：自带前端（ui/index.tsx → ui/index.js，同 §2.3）
```

`Cargo.toml`：

```toml
[package]
name = "my-dll-plugin"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]          # 产出 Windows .dll

[dependencies]
# tb-sdk 是本仓库内的 SDK crate（C ABI 契约 + 宏 + 路径安全）。
# 独立开发时把仓库根下的 tb-sdk/ 目录拷进自己项目（或作为 workspace member），path 引用：
tb-sdk = { path = "../tb-sdk" }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
```

### 4.3 入口样板（tb_plugin! 宏生成全部 FFI 样板）

```rust
//! 插件 id: my-dll-plugin。命令经 plugin_call("my-dll-plugin", ...) 调用。
use serde_json::{json, Value};
use std::ffi::c_void;
use tb_sdk::{emit, tb_plugin, TbHostApi};

/// 插件状态：宿主在 tb_create 时注入配置 JSON（含 vault 路径与应用配置目录）。
pub struct DemoState {
    vault: String,
}

fn state_from_cfg(cfg: &Value) -> Result<DemoState, String> {
    let vault = cfg.get("vault").and_then(|v| v.as_str()).unwrap_or("").to_string();
    if vault.is_empty() { return Err("缺少 vault 配置".to_string()); }
    Ok(DemoState { vault })
}

/// 命令分发：method + params → 结果。写操作后可 emit 事件通知前端。
fn call(
    state: &mut DemoState,
    host: TbHostApi,
    ctx: *mut c_void,
    method: &str,
    params: Value,
) -> Result<Value, String> {
    let vault = state.vault.clone();
    let s = |k: &str| params.get(k).and_then(|v| v.as_str()).map(String::from);
    match method {
        "demo.hello" => {
            let name = s("name").unwrap_or_else(|| "世界".into());
            Ok(json!({ "text": format!("你好，{name}！（vault: {vault}）") }))
        }
        "demo.ping" => {
            // 写操作后发事件：前端 api.on("demo-ping") 收到 { text }
            emit(host, ctx, "demo-ping", json!({ "text": "pong" }));
            Ok(Value::Null)
        }
        _ => Err(format!("未知命令: {method}")),
    }
}

// 宏生成 5 个 #[no_mangle] extern "C" 符号 + panic 隔离（catch_unwind）
tb_plugin!(DemoState, state_from_cfg, call);
```

### 4.4 C ABI 契约与宿主服务表

宏生成的 5 个符号：

| 符号 | 作用 |
|---|---|
| `tb_abi_version() -> u32` | 版本协商（宿主校验 == 3，不匹配拒绝加载） |
| `tb_create(config_json, host) -> handle` | 建实例；`host` = 宿主服务表 `TbHostApi`；失败返回 null |
| `tb_call(handle, method, params) -> *mut c_char` | 调命令，返回统一 `{"ok":true,"result":...}` / `{"ok":false,"error":"..."}` JSON |
| `tb_free_string(s)` | 释放 tb_call 返回的字符串（**必须实现，宿主依赖它回收**） |
| `tb_destroy(handle)` | 销毁实例（Drop 状态）；**有后台线程必须在此收尾**（见 §4.7） |

**TbHostApi 服务表**（宿主回灌，`tb_create` 时传入；回调的 `ctx` 参数是宿主分配的插件
上下文，**插件只透传不解引用**）：

| 回调 | 作用 |
|---|---|
| `emit_event(ctx, event, data)` | 插件 → 前端事件（宿主转发为 `plugin-event`），返回 0 成功 |
| `log(ctx, level, msg)` | 日志（0=info 1=warn 2=error）→ dev 终端 `[plugin:log]` |
| `open_path(ctx, path)` | 用系统默认应用打开文件/文件夹（返回 0 成功） |

`tb-sdk` 提供便捷封装：`tb_sdk::emit(host, ctx, "ev", json)`、`tb_sdk::log(host, ctx, 0, "...")`、
`tb_sdk::now_iso()`（本地时间 `YYYY-MM-DD HH:MM:SS`）。

### 4.5 路径安全（必须）

```rust
use tb_sdk::resolve_safe;
// 拒绝 .. / 绝对路径 / 盘符前缀；规范化后复核防符号链接逃逸
let p = resolve_safe(&vault, rel)?;   // rel 用 / 分隔的 vault 相对路径
```

所有文件操作都必须经它——这是"为什么不会写坏数据"的根基（宿主 `core/path.rs` 同款逻辑）。

### 4.6 构建 DLL → 打包 → UI 安装（完整流程）

```bash
# 1. 构建 release DLL
cargo build --release -p my-dll-plugin
# 产物：target/release/my_dll_plugin.dll（Windows；crate name 的 - 变 _）

# 2. 组装插件目录（目录名 = 插件 id）
my-dll-plugin/
├── plugin.json          # runtime: "native", command: ["my_dll_plugin.dll"]
├── my_dll_plugin.dll
└── ui/                  # 可选：自带前端（同 §2.3）
```

`plugin.json`：

```json
{
  "id": "my-dll-plugin",
  "name": "我的 DLL 插件",
  "version": "0.1.0",
  "runtime": "native",
  "command": ["my_dll_plugin.dll"],
  "description": "Rust DLL 插件示例",
  "permissions": ["fs:read:vault", "fs:write:vault", "log"],

  "nav": [{ "id": "my-dll", "label": "我的 DLL", "icon": "puzzle", "group": "工作区" }]
}
```

```bash
# 3. 打 zip 包（包内结构：plugin.json 在根，或唯一子目录 <id>/plugin.json 均可）
#    PowerShell: Compress-Archive -Path my-dll-plugin -DestinationPath my-dll-plugin.zip

# 4. 应用内安装：插件页 →「安装 .zip / 安装目录」→ 按清单 runtime 部署
#    （native → _core/<id>；webview/process/主题 → 安装根）并默认启用
```

**安装时宿主校验**：id 白名单（拒绝路径穿越）；按 runtime 校验清单完整（native/process 需
`command` 非空，webview 需 `entry` 或声明 `theme`）；zip 解压带 zip-slip 防护（拒绝 `../`
越界条目）。重复安装需先卸载。
**卸载**：插件页卸载 → native 的 `_core\<id>` 目录物理删除（手动安装的 DLL 插件不可恢复，
谨慎）；webview/process/主题插件目录移入回收站。

### 4.7 后台线程与 Drop 收尾（重要）

**若插件开了后台线程（网络服务器、轮询、runtime），必须在 `tb_destroy` 时停掉并 join**，
否则宿主禁用/重载插件即 `FreeLibrary` 卸载 DLL 后，残留线程执行已卸载代码 → 宿主崩溃。
样板：把可停止句柄（`Arc<AtomicBool>` 标志 / `mpsc::Sender` / `Child`）存进 State，实现
`Drop` 收尾（历史参考：已移除的 core-blog/core-ai 插件；git 历史可查）。

### 4.8 在仓库内开发核心插件（可选）

想给 ToolBox 项目贡献核心插件（随应用分发、打安装包时内置）时：

1. 建 `core-plugins/<name>/`（Cargo.toml + src/lib.rs + ui/），tb-sdk 用
   `path = "../../tb-sdk"`。
2. 根 `Cargo.toml` 的 `[workspace].members` 登记新 crate。
3. `scripts/build-core.mjs` 的 `PLUGINS` 数组登记 `{ id, name, description, dll, ui, nav }`。
4. `pnpm build:core` 全量构建（debug DLL + ui → `%APPDATA%/plugins/_core/<id>/`）；
   `pnpm build:core:release` 构建 release 资源（打包版随应用分发）。

## 5. 搜索提供者专题（search.provide 契约）

声明 `"searchProvider": true` 后，宿主 `search_all` 会在每次全局搜索时调用插件的
`search.provide` 命令并把命中并入结果（带 `source: <插件id>` 来源标记）。

**请求**：`{ "query": string, "limit": number }`（limit 由宿主传，当前为 20）。
**响应**：数组 `[{ "path": string, "title": string, "snippet": string }]`。
- `path`：vault 相对路径（供前端打开/定位）。
- `title`：条目标题（宿主把它映射为结果行 filename）。
- `snippet`：命中摘要（"为什么命中"），前端展示。

**建议**（py-tools 的 `search_provide` 已示范）：
- 用 `fs.listDir`（需要 `fs:read:vault` 权限）递归枚举 vault，而不是直接读文件系统——目录
  访问也受权限门控，保持一致。
- 命中结果按 `mtime`（fs.listDir 返回的 UNIX 毫秒）**降序**截取 limit 条——保证"最近修改的
  文件"排在前面（宿主对提供者结果不做排序）。
- 排除隐藏目录与宿主忽略目录（`.git`、`.toolbox`、`node_modules`、`target`、`site`），
  避免备份副本等噪音进搜索结果。

**注意**：宿主对提供者超时 30s；提供者命中过多会被前端与宿主 FTS 结果混排，保持克制（≤limit）。

## 6. 皮肤插件（主题包）详解

给软件"换皮"最轻量的方式：**插件 manifest 声明 `theme` 字段**，提供亮/暗基础 +
令牌覆盖（CSS 变量）+ 可选 CSS 覆盖文件。启用后自动出现在**设置页 → 主题**选择器，
无需任何运行时代码——它是纯数据包（`runtime: "webview"` 且**不写 entry**）。

设计对标 Obsidian/VS Code 的成熟路线：**令牌为主（稳定面）、CSS 选择器为辅（自由面）**。

### 6.1 最小主题插件

```
%APPDATA%\com.toolbox.desktop\plugins\theme-my-skin\
├── plugin.json     ← 声明 theme（含 tokens，可选 css）
└── theme.css       ← 可选：组件级覆盖（不写 css 字段则不需要）
```

`plugin.json`：

```json
{
  "id": "theme-my-skin",
  "name": "我的皮肤",
  "version": "0.1.0",
  "description": "一句话说明",
  "runtime": "webview",
  "theme": {
    "base": "light",                  // "light" | "dark"：决定基础令牌套（tokens.css 的 [data-theme]）
    "tokens": {
      "--bg": "#faf5f0",              // 任意 CSS 变量都可覆盖，不限于下表的常用集
      "--accent": "#a8402c",
      "--radius-md": "16px"
    },
    "css": "theme.css",               // 可选：组件级覆盖文件（相对插件目录）
    "preview": ["#faf5f0", "#a8402c", "#2b211c"]  // 可选：选择器色块（bg/accent/fg 至多 3 色）
  },
  "config": {}
}
```

- **id 规则**与其他插件一致（小写字母/数字开头，仅小写字母/数字/`-`，= 目录名）。
- 主题 id = 插件 id，天然全局唯一；**纯主题插件可省略 `entry`**（校验放行）。
- 安装方式与 webview 插件相同：把目录复制进插件根（或仓库内开发后 `pnpm sync:plugins`），
  插件页"刷新"发现 → **启用** → 设置页主题选择器出现该主题 → 点击应用。
- 禁用/卸载插件 = 主题从选择器消失；若当时正在用该主题，自动回落默认亮色。

### 6.2 双通道：令牌（稳定面） + CSS（自由面）

| 通道 | 写法 | 能做什么 | 稳定性 |
|---|---|---|---|
| **tokens**（manifest 内 JSON） | `"--accent": "#a8402c"` | 全部颜色 / 字体 / 字号 / 间距 / 圆角 / 阴影 | ✅ 稳定契约：覆盖宿主所有引用该变量的组件，宿主改版不碎 |
| **css**（theme.css） | `[data-part="topbar"] { ... }` | 组件级视觉：形状、聚焦态、隐藏/重排、动效 | ⚠️ 依赖宿主类名/钩子：见下方"公开契约"，宿主大改版可能碎 |

**应用机制**：tokens 经宿主 `<style id="theme-overrides">` 注入（与内置主题同机制，
作用域 `:root[data-theme-id="<id>"]`）；css 文件经 `plugins_read_file` 读取后**全局注入**
（`<style id="theme-plugin-css">`），切换主题即移除。两通道互不阻塞：css 读取失败只告警，
令牌照常生效。

**推荐写法**：所有选择器带 `:root[data-theme-id="<id>"]` 前缀（见下方示例），保证
"只在你的主题激活时生效"，切换瞬间无串色。仓库 `plugins/theme-maple`（枫叶红）是完整示例。

### 6.3 公开 CSS 契约（皮肤开发必须知道）

宿主外壳组件提供稳定钩子（`data-part` 属性，组件根节点）：

```html
<div data-part="app">          <!-- 应用壳 -->
  <header data-part="topbar">    <!-- 顶栏（.topbar） -->
  <nav data-part="sidebar">      <!-- 侧边栏（.sidebar，折叠时加 .collapsed） -->
  <main data-part="main">        <!-- 主内容区（.main） -->
  <footer data-part="statusbar"> <!-- 状态栏（.statusbar） -->
</div>
```

**稳定公开**（皮肤可放心使用，宿主保证语义不变）：
`data-part` 五钩子 + 下列类名：`.topbar` / `.sidebar` / `.main` / `.statusbar`、
`.topbar-brand` / `.topbar-title` / `.workspace-btn` / `.search` / `.search-input` /
`.search-dropdown` / `.search-item`（`.active` 选中态）/ `.search-meta`、
`.nav-group` / `.nav-label` / `.nav-group-head` / `.nav-item`（`.active`）、
`.status-dot`、`.view-header`、`.settings-card`、`.theme-card`、`.btn`（`.btn-sm` /
`.btn-primary` / `.btn-ghost`）、`.empty-state`、`.icon-btn`。

**内部可变**（皮肤用了可能碎）：其余类名与所有布局细节（宽度/高度/内边距/弹性顺序）。
实现原则：**优先用 tokens 覆盖变量，CSS 只做 tokens 表达不了的形状/布局微调**。

> 设计令牌全集见 `src/styles/tokens.css`（颜色/字体/字号/间距/圆角/动效 + 语义色），
> 组件样式见 `src/styles/app.css`（全部引用 var()，仅个别硬编码）。

### 6.4 示例：枫叶红（plugins/theme-maple）

仓库里有两个完整示例可对照：**`plugins/theme-maple`（亮色）** 与 **`plugins/theme-midnight`（暗色，
`"base": "dark"`）**——同一套契约，两种底色基调；暗色示例演示了 `base` 切换驱动整套暗色令牌。

`theme.css` 片段（完整文件见仓库）：

```css
/* 只在本主题激活时生效 */
:root[data-theme-id="theme-maple"] [data-part="topbar"] {
  border-bottom-color: var(--accent-soft);
}
:root[data-theme-id="theme-maple"] .search {
  border-radius: 999px;            /* 搜索框变胶囊 */
}
:root[data-theme-id="theme-maple"] .search:focus-within {
  border-color: var(--accent);
  box-shadow: 0 0 0 3px var(--accent-soft);
}
```

### 6.5 主题能力边界

- **能做到**：全部配色 / 字体 / 字号 / 间距 / 圆角 / 阴影；组件级视觉覆盖
  （形状、聚焦态、隐藏元素、flex 重排"布局感觉"、动效）。
- **做不到**：外壳结构替换（换掉顶栏/侧栏组件本体）、宿主组件增删——那是架构级改动，
  主流产品（Obsidian/VS Code）同样不做，皮肤定位就是"换皮不换骨"。
- **DLL / Python 插件做不了皮肤**：CSS 注入需要与界面同 document（webview 运行时）；
  process/native 插件只能当"主题生成器"（按算法产出 tokens JSON 供前端加载）。

### 6.6 常见问题

| 现象 | 排查 |
|---|---|
| 设置页主题选择器不出现 | 插件未启用（插件页启用）；plugin.json 的 theme 缺 base（或 base 非 light/dark，清单解析报错） |
| 颜色生效但 CSS 覆盖不生效 | css 字段路径写错 / 文件不存在（看 dev 终端 `[theme]` 告警）；选择器没带 `data-theme-id` 前缀时检查是否被宿主规则覆盖（提高特异性） |
| 切回默认主题后皮肤样式残留 | 正常情况切走即移除；若残留，确认宿主未缓存 `<style id="theme-plugin-css">`（重启页面再试） |
| 皮肤里想改布局 | 用 flex 重排/隐藏（CSS 可行）；改组件结构不行（见 6.5） |

### 6.7 皮肤插件与备份

- **自动纳入备份**：皮肤插件与其他外部插件一样在全局插件目录（默认 `%APPDATA%\com.toolbox.desktop\plugins\`，可在插件页自定义），
  每次备份会随 `_plugins/` 存档复制（`_core` 核心插件除外）；备份列表会显示「插件」徽标。
- **恢复时不自动还原**：恢复只回写 vault 内容，`_plugins` 存档不覆盖全局插件目录（安全设计——
  插件可能含代码，恢复旧版本插件有风险）。需要时从备份的 `_plugins\<id>\` 手动复制回全局插件目录即可。
- **分享皮肤**：把插件目录（`plugin.json` + `theme.css`）打包 zip 发给别人，对方复制进全局插件目录
  并在插件页启用即可（与 webview 插件安装一致，见 §0.2）。

## 7. 宿主外壳扩展点（顶栏动作 / 托盘菜单 / 设置面板）

宿主外壳（顶栏 / 托盘 / 设置页）默认只渲染框架自身内容。插件可通过 manifest
**声明式**扩展这些位置，无需改宿主代码：

### 7.1 外壳动作（顶栏图标按钮 / 托盘菜单项）

```json
{
  "actions": [
    { "id": "greet", "label": "示例问候", "icon": "puzzle", "topbar": true, "tray": true },
    { "id": "open",  "label": "打开示例界面", "icon": "file-text", "topbar": false, "tray": true }
  ]
}
```

- `topbar: true` → 顶栏渲染图标按钮（icon 用宿主内置图标名，如 puzzle/gear/file-text）
- `tray: true` → 托盘菜单渲染「插件名：label」项
- `file: true` → **文件上下文动作**：宿主「文件」视图（浏览当前工作区）的右键菜单与
  多选批量操作条显示该动作；触发时把**选中的工作区相对路径列表**传给插件（见 §7.1b）
- **交互契约（统一，不感知来源）**：点击 → 宿主做两件事：
  1. 发 `plugin-event` 事件 `action`（payload `{action, source}`，source =
     `topbar | tray | file`；file 时附 `files: [rel, ...]`）→ **插件自带前端 UI**
     用 `api.on("action")` 订阅响应
  2. 非 webview 插件调约定命令 `plugin.action {action, source, files?}` → **纯逻辑**
     （native/process）响应；未实现该命令则忽略（事件通道已发出）
- 示例：`core-example` 的 `plugin.action` 命令 + 主界面/设置面板的事件日志
- 托盘插件段随插件启停自动重建（宿主监听 `plugins-changed`）

### 7.1b 文件上下文动作（插件决定"怎么组织工作区的文件"）

2026-09 起宿主的定位是：**框架本体提供完整的文件处理基础能力**（浏览/新建/重命名/
移动/复制/删除/搜索/批量，`files_*` 命令，全部 S1c 校验只作用于当前工作区），
**插件决定文件处理的表现形式与业务逻辑**。文件上下文动作就是插件在这套能力之上的
挂钩点——用户在宿主文件视图里选中文件/目录（单选或批量），右键菜单 / 底部操作条里
出现插件的动作，点击后宿主把选中项传给插件，由插件执行自己的组织逻辑
（建目录结构 / 按规则归类 / 转格式 / 改名…）。

```json
{
  "actions": [
    { "id": "init-project-structure", "label": "初始化探针卡项目结构", "icon": "folder", "file": true },
    { "id": "archive-to-batch",       "label": "归档到批次目录",       "icon": "folder", "file": true }
  ]
}
```

插件侧（`plugin.action` 命令）收到：

```json
{ "action": "archive-to-batch", "source": "file", "files": ["数据/raw.xlsx", "报告/a.lst"] }
```

- `files` 是**工作区相对路径**（`/` 分隔），拼接 `TB_WORKSPACE`（当前工作区绝对路径，
  见 §3.10）即得绝对路径——**务必做越界校验**（`os.path.commonpath` / 前缀判断），
  宿主协议测试里对 `../` 逃逸有断言（probe-rat-layer 的 `plugin.action` 演示）。
- 宿主文件视图在插件动作返回后自动刷新列表（插件可能改了结构）。
- 完整实现示例：`core-plugins/probe-rat-layer/src/dispatch.rs` 的 `cmd_plugin_action`
  （初始化项目结构 + 按批次归档，含 `_safe_join` 越界防护），离线验证见该插件
  Rust 测试（`dispatch_command_routing` 等）。
- **表现层自由**：动作只负责"处理"；要复杂界面（拖拽组织/结构预览）就在插件的自带
  前端（ui/index.ts）里做，用宿主 `api.fs*` 命令读写文件——宿主文件视图是"通用入口"，
  插件自带前端是"定制表现"。

### 7.2 设置页插件段（插件自己的设置面板）

```json
{ "settings": { "entry": "ui/settings.js" } }
```

- 设置页出现「插件设置」段，宿主把 `ui/settings.js`（自包含 IIFE）挂载进该段
- 注册 key 约定：`window.__TB_PLUGIN_UI__["settings:<pluginId>"]`；桥与主界面同构
  （`api.call` / `api.on` / `api.context` 均可用）
- 建议设置面板不写 `<style>` 块（复用宿主全局 `.settings-*` class + 内联样式，
  避免与主界面 style.css 产物冲突）
- 示例：`core-example` 的 `ui/settings.ts` + `ui/SettingsPanel.vue`

### 7.3 通用说明

- 三类插件（webview/process/native）都能声明 actions / settings；settings 面板
  需要自带前端（UI），process/webview 插件用 `build-external-ui` 构建
- 插件启停/卸载后顶栏与托盘自动跟随（宿主遍历启用插件渲染）；设置段同理
- 需要更多外壳位置（状态栏、全局快捷键、托盘子菜单等）→ 宿主加扩展点，机制同
  本节的声明式模式

## 8. 调试与常见问题

### 7.1 日志与调试手段

- **process / native**：stderr → dev 终端（`pnpm tauri dev` 窗口），`[plugin:log]` / `[plugin:<id>]` 前缀。
- **webview**：`console.log` → dev 终端（`[plugin:<id>]` 前缀）；入口加载失败会在插件页显示错误。
- 插件页有**实时事件流**（可观察事件推送）与**命令试用台**（填 JSON 调任意命令）。
- 插件目录改动：webview 刷新页面重载；process/native 在插件页点"重载"。

### 7.2 常见问题速查

| 现象 | 排查 |
|---|---|
| 插件页不出现 | 目录名 ≠ plugin.json 的 id；plugin.json 非法（页面显示解析错误）；忘了复制到 `%APPDATA%` 插件根 |
| 命令调用报"未注册" | webview：入口未 `registerCommand` 或入口加载失败（看插件页错误状态）；process：init 未声明该命令 |
| 权限报错 | 调 `fs.*` 需在 permissions 声明 `fs:read:vault` / `fs:write:vault` |
| native 插件拒绝启动 | 目录不在 `_core` 下（见 §4.1）；ABI 版本不匹配（需升级 tb-sdk 重编译）；DLL 缺符号（tb_create 等） |
| 插件挂死/超时 | 30s 超时会终止进程并提示；检查死循环 / 等待输入 / 不消费 stdin |
| 崩溃自动重启 | 60s 窗口内最多 3 次，之后标记错误；看 stderr |
| 中文乱码（process） | Windows 管道默认 GBK：`stdin/stdout.reconfigure(encoding="utf-8")` |
| 改前端不生效 | 自带前端需重新构建（`pnpm build-external-ui plugins/<id>`）+ 重载；**dev 运行中重建可能被 exe 锁挡住，先停 dev** |
| 事件收不到 | 事件经 `plugin-event` 总线；`api.on(event)` 默认过滤本插件 id，跨插件需传 targetPluginId |
| webview 入口报 `process is not defined` | 构建时未 define `process.env.NODE_ENV`（见 §2.3） |
